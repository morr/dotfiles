# Патч: code-review → описание PR как часть спеки + интерактивный обход найденных issue

**Цель патча, часть 1 (ось Spec):** спека — это **два документа**, а не один. Issue говорит,
что просили; **описание PR** говорит, о чём договорились уже по ходу работы, и там же
зафиксированы осознанные расхождения с исходными требованиями. Скилл обязан прочитать
описание PR (сырым markdown) и передать его саб-агенту Spec отдельным блоком.

**Цель патча, часть 2 (обход):** после того как обе оси отработали, скилл не «выдаёт отчёт
и заканчивает», а идёт **циклом по каждой найденной проблеме**: детальный разбор →
план фикса от `fable-planner` (на каждую issue) → вопрос оператору
«фиксить / не фиксить» с возможностью комментария → применение фикса → следующая проблема.
Начало каждой issue визуально отбито, чтобы переходы были различимы в длинном транскрипте.

Наложить на: `~/.claude/skills/code-review/SKILL.md` (единственный файл скилла;
`agents/openai.yaml` не трогаем).

Скилл ставится из набора Matt Pocock — переустанавливается через `/setup-matt-pocock-skills`,
то есть патч затирается.

## Что делает апстрим

1. Фронтматтер `description`: «Runs both reviews in parallel sub-agents and **reports them
   side by side**».
2. Шаг «### 2. Identify the spec source» знает **только один** источник спеки — issue из
   коммит-сообщений, путь-аргумент или файл под `docs/`/`specs/`/`.scratch/`. Про PR ветки
   в нём нет ни слова, и саб-агент Spec его описания не видит.
3. Шаг «### 5. Aggregate» — единственный финальный шаг: положить два отчёта саб-агентов под
   заголовками `## Standards` и `## Spec` «verbatim or lightly cleaned», закончить
   однострочным summary (сколько находок на ось + худшая внутри каждой оси). На этом скилл
   заканчивается: никакого разбора по одной, никакого запроса резолюции, никаких фиксов.
4. Брифы саб-агентов на шаге 4 не требуют нумерованного списка — саб-агент может вернуть
   связный текст, который потом нечем индексировать.

## Почему это меняем

- **Описание PR — часть спеки.** Пока ветка в работе, часть исходных требований issue
  сознательно пересматривается, и запись об этом живёт в описании PR (его в этом репозитории
  пишет `/pr_description`), а не в issue. Саб-агент, который видит только issue, приносит
  такие расхождения как находки — оператор раз за разом отвечает «так и задумано». Правило
  приоритета: расхождение, **явно описанное** в PR, — решение, а не дефект; расхождение,
  о котором описание молчит, — по-прежнему находка; а утверждение описания, которого нет
  в диффе, — тоже находка (устарело описание или неверен код, решает оператор).
- Описание тянем сырым markdown (`gh pr view --json body`) — по правилу репозитория
  отрендеренный вид режет картинки и ссылки на файлы, а в этом трекере вложения — половина
  требований.
- Summary всех проблем — не то, что нужно: нужен **обход по одной** с резолюцией оператора
  по каждой (фиксить / не фиксить, к обоим вариантам — комментарий). Ровно это пришлось
  диктовать руками поверх скилла в сессии `mobile-notifications-review` (22–23.08.2026).
- Нетривиальный фикс лучше сначала спланировать — для этого в проекте есть агент
  `fable-planner`; его описание требует явного упоминания Fable, и вызов из скилла
  как раз является таким явным требованием (это оговорено в тексте патча).
- В том же прогоне переход между issue терялся: строка `Issue 14/27 — …` шла обычным
  абзацем сразу за отчётом о фиксе предыдущей. Нужен жёстко заданный визуальный якорь,
  а не «как получится».
- Разделение осей апстрима сохраняем: находки не смешиваются и не переранжируются,
  сквозная нумерация нужна только чтобы у issue был стабильный id.

## Правки

### Фронтматтер

`description`: `Runs both reviews in parallel sub-agents and reports them side by side.`
→ `Runs both reviews in parallel sub-agents, then walks the findings one by one — detail,
suggested fix, and a fix / don't-fix resolution from the user for each.`

Там же в скобках после оси Spec: `(does the code match what the originating issue/spec asked
for, as amended by the decisions recorded in the PR description?)`.

### Вступление (абзац «Both axes run as parallel sub-agents…»)

Буллет оси Spec: `does the code faithfully implement the originating issue / spec` →
`…, together with the decisions the PR description records on top of it?`.

`then this skill aggregates their findings` → `then this skill walks their findings with the
user — one issue at a time, each with a resolution`, и следом отдельным абзацем жирным:
**The review is not the deliverable, the walk is** — summary всего найденного никогда не
последнее, что печатается; скилл заканчивается, когда у каждой issue есть резолюция.

### Шаг 2 «Identify the spec source» → «Identify the spec sources — the issue *and* the PR description»

Открывающая фраза: спека — **два документа**, issue (что просили) и описание PR (о чём
договорились по ходу); собрать оба **до** запуска саб-агентов. Дальше три подпункта:

- **a. The originating spec** — прежний нумерованный список апстрима 1–4, без изменений,
  кроме хвоста пункта 4: если спеки нет, саб-агент Spec работает по одному описанию PR,
  и только когда нет и его — пишет «no spec available».
- **b. The PR description** — тянуть **сырым markdown**, не отрендеренный вид (режет
  картинки и ссылки на файлы), двумя командами: `gh pr view --json number,title,body,url`,
  а если PR текущей ветки не нашёлся — `gh pr list --head "$(git rev-parse --abbrev-ref
  HEAD)" --json number,title,body,url`. Нет PR — сказать строкой и продолжить по issue,
  это не блокер.
- **c. How the two combine** — правило приоритета тремя буллетами: явно описанное в PR
  расхождение с issue — **решение, а не дефект**, в находки не идёт (и прямо сказано, что
  ровно ради этого шаг и существует); расхождение, о котором описание молчит, — находка;
  само описание тоже ревьюим — обещание описания, которого нет в диффе, и поведение диффа,
  о котором описание молчит, — находка оси Spec. Плюс: два текста передавать **раздельно**,
  не сливая в один «spec».

### Шаг 4 (брифы саб-агентов)

В конец обоих брифов (Standards и Spec) добавить требование возвращать находки
**discrete numbered items**, каждая с файлом и строками, — иначе результат нечем
индексировать на шаге 5.

В бриф Spec дополнительно:

- во входные данные — **отдельный помеченный блок с телом описания PR** из шага 2b (или
  строка «the branch has no PR»); подчёркнуто, что путь не годится, нужно вставить текст:
  у саб-агента другого доступа к нему нет;
- в перечень отчёта — пункт `(d)`: обещания описания PR, которых дифф не выполняет, и
  поведение диффа, о котором описание молчит; цитировать строку спеки **или** строку
  описания PR;
- правило приоритета внутри брифа: `The PR description outranks the issue where it
  explicitly says so` — такие расхождения не репортить, а перечислить одной closing-строкой
  («что я счёл решённым»), чтобы оператор видел, что было снято;
- условие пропуска саб-агента: «если нет спеки» → «если нет **и** спеки, **и** описания PR».

### Шаг 5 «Aggregate» → «Index the findings»

Целиком заменить: вместо двух отчётов verbatim + summary — **один нумерованный индекс**,
строка на issue:

```
N. [Standards|Spec] · [hard|judgement] · path/to/file.rb — title, ≤12 words
```

Правила: не вставлять прозу саб-агентов (детали — в карточку шага 6, после собственной
перепроверки кода); оси помечены и не переранжируются, нумерация сквозная (сначала блок
Standards, потом Spec); одна и та же строка кода, найденная обеими осями, — это две issue;
после индекса **сразу** шаг 6, без вопроса «идти ли по списку».

### Новый шаг 6 «Walk the issues, one at a time»

Пункты a–f:

- **a. Verify it yourself first** — перечитать код, на который ссылается саб-агент; находка
  это гипотеза. Не подтвердилась — так и пишем в карточке, но резолюцию всё равно спрашиваем.
- **b. Баннер** — заданной формы, дословно: горизонтальная линейка, затем заголовок
  `## ▌ISSUE 7/22 · Standards · judgement`, затем строка-локатор с файлом и коротким
  заголовком. Оговорено: `▌` не встречается больше нигде в выводе, и ни одна issue без
  баннера не начинается.
- **c. Карточка** — **детальный** разбор, печатается обычным текстом сообщения **до**
  вопроса (не внутри description у `AskUserQuestion` — виджет показывает одну строку, а
  оператор решает по карточке). Строка индекса карточкой не является: карточка, уместившаяся
  в одну строку, не написана. Четыре секции: `Где` (каждый файл и диапазон строк, и под
  каждым — **реальный код в fenced-блоке**, как он лежит на диске, не пересказ и не дифф;
  для локали — ключ и значение, для Spec — трасса вызовов по файлам) / `Что не так` (прозой,
  2–5 предложений: что код делает сейчас, что должен, что сломается, если оставить) /
  `Почему` (дословная цитата стандарта, строки спеки **или строки описания PR**; для запаха
  из baseline — назвать запах и что это judgement; перед этой строкой на issue оси Spec —
  самому перечитать описание PR: если расхождение там зафиксировано, пишем это в карточке
  и помечаем issue `снято описанием PR`, но резолюцию всё равно спрашиваем — оператор вправе
  передумать) / `План фикса` (план из пункта d нумерованными шагами, тест первым; **каждый
  шаг, меняющий файл, — diff, а не слова**: fenced-блок ```` ```diff ````, первой строкой
  `path:строки`, затем `-`/`+` с реальным текстом с диска (с отступами) и 1–2 строками
  контекста — та же форма, что печатает Edit. Новый файл — целиком `+`-строками, перенос
  блока — два хунка, добавляемый спек — сам пример `+`-строками под его `describe`/`context`.
  Никаких `'old' → 'new'` и «переименовать X в Y» прозой: оператор утверждает ровно те байты,
  которые лягут, и на «Фиксить» пункт f применяет этот diff, а не пишет заново. Текстом —
  только шаги без файлов: какой существующий спек уже покрывает и почему ничего не
  добавляется, что планер сознательно не тронул, и в конце команды проверки: пути спеков,
  rubocop по затронутым файлам. В скилле — пример такого блока на одну строку.)
- **d. Fable-план — на каждую подтверждённую issue**, без порога «нетривиальности»:
  `Agent` с `subagent_type: "fable-planner"`, на вход — секции карточки `Где`/`Что не так`/
  `Почему`, пути, применимые стандарты репозитория и ограничение «test-first, не шире
  issue»; просить вернуть каждое изменение файла **diff-хунком** (`path:строки`, `-`/`+`
  с реальным текстом), прозу — только для шагов без файлов, т.е. уже в формате
  `План фикса`, чтобы план лёг в карточку без переписывания; план сжать в секцию
  `План фикса` (оператор читает план через карточку, не через сырой вывод агента). Явно сказано, что вызов из скилла = то самое явное упоминание Fable,
  которого требует описание агента. Планер зовётся и на однострочную правку: именно он
  замечает второй call site, отсутствующий спек или слово из глоссария за «однострочником».
  Не зовётся только для `не подтвердилось` и `снято описанием PR` — планировать нечего.
- **e. Резолюция** — один `AskUserQuestion` на issue, никогда не батчем: header `Issue N`,
  опции **«Фиксить»** / **«Не фиксить»** с описанием последствий; комментарий оператора
  приходит свободным ответом и записывается дословно, а также исполняется (может сузить фикс,
  а не только объяснить отказ).
- **f. Действие и закрытие** — фиксим: правка + спек + прогон затронутых спеков и линтеров,
  отчёт в 1–3 строки (включая падение, если упало); не фиксим: записать комментарий.
  В обоих случаях финальная строка `Issue N — пофикшено / не фиксим`, и следующее, что
  печатается, — **баннер следующей issue**.

Плюс запреты: две issue в одном сообщении, продолжение без ответа на вопрос, тихое выпадение
issue из индекса.

### Новый шаг 7 «Ledger»

После закрытия последней issue — таблица `| # | Ось | Issue | Резолюция | Комментарий |`
в порядке индекса, плюс короткий список того, что реально изменилось на диске, и что осталось
падать. Это единственное место, где уместен общий обзор.

Секцию «Why two axes», шаг 1, шаг 3 и smell baseline не трогать.

### Что при этом появилось в issue-walk (для понимания, патча не требует)

- **Слот 8 «Planner model»** — дефолт «не задан» (шаг 0 спрашивает); задан — шаг 0
  пропускается целиком, модель уходит на каждый спавн планировщика.
- **Слот 9 «Decision mode»** — дефолт `manual`; `auto` меняет ровно две вещи: вопрос на
  итерации и размер карточки. Индекс, баннер, окно планировщиков, фиксы, спеки и ledger стоят.
- В `auto` карточка — **заглушка в 2–3 строки**; полная четырёхсекционная печатается только
  на issue, где обход остановился.
- Планировщик в `auto` возвращает строку `Резолюция оператора: нужна / не нужна — почему`
  по фиксированному списку критериев (фикс выходит за пределы дифа; план сознательно берёт
  риск; меняется доменное поведение или публичный контракт, а не форма кода; два равноправных
  варианта фикса; надо ослабить или удалить существующий спек; находка спорит с записанным
  решением). Решает планировщик, потому что он единственный здесь читал код.
- Триггеры самого walker'а, не требующие чтения кода: красный фоновый прогон, протухшие
  якоря плана после переспавна, путь из `db/migrate/**`, `config/locales/**`,
  `config/credentials/**` или файл вне ревьюируемого изменения.
- Остановка — исключение одной issue, а не переключение режима.
- Ledger в `auto`: в колонке `Резолюция` — `(авто)` / `(спрошено)`, строка со счётом
  остановок, и после таблицы **сводка изменений** прозой — по файлу: что было, что стало и
  какая находка это подвинула.

Замер прогона `/code-review opus auto`: фаза запуска Standards-агентов заняла 5 минут, при том

напечатанное трижды, причём список запахов уже лежал в контексте как часть скилла.

**Новый файл `smells.md` в директории скилла** — переустановка его снесёт, поэтому он часть

**Шаг 3** — 12 буллетов и абзац «Each smell reads…» убраны, вместо них два абзаца: что такое

запретом читать и пересказывать его самому — единственный его читатель — саб-агент шага 4.

**Шаг 4** — три новых абзаца перед брифами:

- **«Parallel means one message, not one after another»** — все агенты обзора уходят одним
  блоком `Agent`-вызовов в одном сообщении: и две оси, и те несколько агентов, на которые

- **«Give a sub-agent a path, never a paste, for anything that is already a file»** — промпт

Плюс в bullet'е брифа Standards «plus the smell baseline from step 3 pasted in full» заменено
на «plus the absolute path of the smell baseline, with the instruction to read that file first».

### Что при этом появилось в issue-walk (для понимания, патча не требует)

Парные правки того же замера, уже закоммичены в репозитории:

- Окно планировщиков в `auto` — **восемь** вместо четырёх: в `auto` обход доходит до каждой
  issue, так что план впустую не пропадает, а сама issue закрывается за время печати заглушки,
  пока планировщик считает минутами (80–517 с против ~90 с на issue — окно из четырёх дало два
  простоя, 5 и 3.5 минуты).
- В `auto` планировщик возвращает **заглушку и детальный план**, а не всю карточку: *Где* с
  ханками, *Что не так* прозой, дословное *Почему* и короткий план там не читает никто —
  примерно половина каждого отчёта. Основание — одной строкой (его требует сводка изменений),
  детальный план диффами не меняется (его применяет шаг 2f, по его `-`-строкам идёт проверка
  на устаревание). Эскалирующий планировщик возвращает полную карточку, потому что на такой
  issue обход останавливается и идёт как `manual`.
- Заглушку в `auto` пишет планировщик, а не walker.
