# Патч: code-review → интерактивный обход найденных issue вместо summary

**Цель патча:** после того как обе оси отработали, скилл не «выдаёт отчёт и заканчивает»,
а идёт **циклом по каждой найденной проблеме**: детальный разбор → suggested fix →
(при нетривиальном фиксе) план от `fable-planner` → вопрос оператору «фиксить / не фиксить»
с возможностью комментария → применение фикса → следующая проблема. Начало каждой issue
визуально отбито, чтобы переходы были различимы в длинном транскрипте.

Наложить на: `~/.claude/skills/code-review/SKILL.md` (единственный файл скилла;
`agents/openai.yaml` не трогаем).

Скилл ставится из набора Matt Pocock — переустанавливается через `/setup-matt-pocock-skills`,
то есть патч затирается.

## Что делает апстрим

1. Фронтматтер `description`: «Runs both reviews in parallel sub-agents and **reports them
   side by side**».
2. Шаг «### 5. Aggregate» — единственный финальный шаг: положить два отчёта саб-агентов под
   заголовками `## Standards` и `## Spec` «verbatim or lightly cleaned», закончить
   однострочным summary (сколько находок на ось + худшая внутри каждой оси). На этом скилл
   заканчивается: никакого разбора по одной, никакого запроса резолюции, никаких фиксов.
3. Брифы саб-агентов на шаге 4 не требуют нумерованного списка — саб-агент может вернуть
   связный текст, который потом нечем индексировать.

## Почему это меняем

- Summary всех проблем — не то, что нужно: нужен **обход по одной** с резолюцией оператора
  по каждой (фиксить / не фиксить, к обоим вариантам — комментарий). Ровно это пришлось
  диктовать руками поверх скилла в сессии `mobile-notifications-review` (22–23.08.2026).
- Нетривиальный фикс лучше сначала спланировать — для этого в проекте есть агент
  `fable-planner`; его описание требует явного упоминания Fable, и вызов из скилла
  как раз является таким явным требованием (это оговорено в тексте патча).
- В том же прогоне переход между issue терялся: строка `Issue 14/27 — …` шла обычным
  абзацем сразу за отчётом о фиксе предыдущей. Нужен жёстко заданный визуальный якорь,
  а не «как получится».
- Разделение осей апстрима сохраняем: находки не смешиваются и не переранжируются,
  сквозная нумерация нужна только чтобы у issue был стабильный id.

## Правки

### Фронтматтер

`description`: `Runs both reviews in parallel sub-agents and reports them side by side.`
→ `Runs both reviews in parallel sub-agents, then walks the findings one by one — detail,
suggested fix, and a fix / don't-fix resolution from the user for each.`

### Вступление (абзац «Both axes run as parallel sub-agents…»)

`then this skill aggregates their findings` → `then this skill walks their findings with the
user — one issue at a time, each with a resolution`, и следом отдельным абзацем жирным:
**The review is not the deliverable, the walk is** — summary всего найденного никогда не
последнее, что печатается; скилл заканчивается, когда у каждой issue есть резолюция.

### Шаг 4 (брифы саб-агентов)

В конец обоих брифов (Standards и Spec) добавить требование возвращать находки
**discrete numbered items**, каждая с файлом и строками, — иначе результат нечем
индексировать на шаге 5.

### Шаг 5 «Aggregate» → «Index the findings»

Целиком заменить: вместо двух отчётов verbatim + summary — **один нумерованный индекс**,
строка на issue:

```
N. [Standards|Spec] · [hard|judgement] · path/to/file.rb — title, ≤12 words
```

Правила: не вставлять прозу саб-агентов (детали — в карточку шага 6, после собственной
перепроверки кода); оси помечены и не переранжируются, нумерация сквозная (сначала блок
Standards, потом Spec); одна и та же строка кода, найденная обеими осями, — это две issue;
после индекса **сразу** шаг 6, без вопроса «идти ли по списку».

### Новый шаг 6 «Walk the issues, one at a time»

Пункты a–f:

- **a. Verify it yourself first** — перечитать код, на который ссылается саб-агент; находка
  это гипотеза. Не подтвердилась — так и пишем в карточке, но резолюцию всё равно спрашиваем.
- **b. Баннер** — заданной формы, дословно: горизонтальная линейка, затем заголовок
  `## ▌ISSUE 7/22 · Standards · judgement`, затем строка-локатор с файлом и коротким
  заголовком. Оговорено: `▌` не встречается больше нигде в выводе, и ни одна issue без
  баннера не начинается.
- **c. Карточка** — `Где` (файлы, цитата строк) / `Что не так` / `Почему` (дословная цитата
  стандарта или строки спеки; для запаха из baseline — назвать запах и что это judgement) /
  `Suggested fix` (какие файлы, какая новая форма, какой спек это докажет).
- **d. Fable-план** — если фикс трогает больше ~2 файлов, меняет схему/API/доменный словарь
  или имеет несколько вариантов: `Agent` с `subagent_type: "fable-planner"`, план сжать в
  карточку. Явно сказано, что вызов из скилла = то самое явное упоминание Fable, которого
  требует описание агента. На однострочные правки и тексты локалей — не звать.
- **e. Резолюция** — один `AskUserQuestion` на issue, никогда не батчем: header `Issue N`,
  опции **«Фиксить»** / **«Не фиксить»** с описанием последствий; комментарий оператора
  приходит свободным ответом и записывается дословно, а также исполняется (может сузить фикс,
  а не только объяснить отказ).
- **f. Действие и закрытие** — фиксим: правка + спек + прогон затронутых спеков и линтеров,
  отчёт в 1–3 строки (включая падение, если упало); не фиксим: записать комментарий.
  В обоих случаях финальная строка `Issue N — пофикшено / не фиксим`, и следующее, что
  печатается, — **баннер следующей issue**.

Плюс запреты: две issue в одном сообщении, продолжение без ответа на вопрос, тихое выпадение
issue из индекса.

### Новый шаг 7 «Ledger»

После закрытия последней issue — таблица `| # | Ось | Issue | Резолюция | Комментарий |`
в порядке индекса, плюс короткий список того, что реально изменилось на диске, и что осталось
падать. Это единственное место, где уместен общий обзор.

Секцию «Why two axes», шаги 1–3 и smell baseline не трогать.
